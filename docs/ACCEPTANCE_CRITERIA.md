Вы предложили определиться вместе. Я подготовил основу: **числовые
критерии посчитаны по вашим текстам** (43 606 слов двух диссертаций),
их проверять не надо — они уже измерены. От вас нужны только
**содержательные**. Все семь получили ответ заказчика и перенесены в код

Формат: что проверяем автоматически (машина) / что решает человек.

## Базовые пороги для всех текстовых этапов

Посчитано по эталону — обеим диссертациям:

| Метрика | Эталон автора | Порог приёмки | Почему так |
|---|---|---|---|
| Разброс длин предложений | 18.2 | **≥ 12.7** (70% эталона) | Главный маркер ИИ. Живая генерация давала 8.2 — брак |
| Средняя длина предложения | 20.3 слов | 15–26 | Выше → «вода» |
| Доля коротких (<8 слов) | 17.4% | **≥ 10%** | У ИИ было 0% — ни одного короткого |
| Доля длинных (>30 слов) | 15.4% | ≤ 22% | Автор их использует, запрещать нельзя |
| Клише на 1000 слов | 1.95 | **≤ 2.0** | НЕ ноль: автор сам пишет «таким образом» 46 раз |
| Абзац | 198 слов | 120–280 | |

⚠️ **Важное уточнение по клише.** В работе 2002 года: «таким образом» ×29,
«в целом» ×22. В работе 2026: ×17 и ×4. Промпт запрещает эти обороты
полностью — это строже, чем пишет сам автор. Если требовать ноль,
humanizer будет бесконечно переписывать текст, который УЖЕ похож на эталон.
Порог 2.0/1000 слов — «не хуже автора».

✅ **РЕШЕНО:** порог «не выше авторского». Жёсткий ноль оставлен как
опция `cliche_policy="strict"`, но по умолчанию выключен.

## 1. `analysis` — анализ темы

**Машина проверяет:**
- есть 3–5 тезисов ядра темы
- есть логическая дуга (порядок раскрытия)
- есть 5–7 направлений поиска источников
- есть блок рисков шаблонности
- каждое непроверенное утверждение помечено `[нужно проверить: ...]`
- НЕ содержит готового текста работы (нет абзацев прозы > 500 знаков)

**Брак:** выдал готовое введение вместо заметок; ни одной пометки
`[нужно проверить]` при наличии конкретных дел/сумм.

✅ **РЕШЕНО:** зависит от темы. «Для сложной и многогранной темы нужно
раскрыть нюансы, и пунктов будет больше». Поэтому в настройках задаётся
диапазон `theses_per_section` (по умолчанию 3–8), а не одно число.

## 2. `plan` — план работы

**Машина:**
- 2–3 главы (или 3, как в обеих ваших работах)
- 2–4 параграфа на главу, нумерация 1.1, 1.2, 2.1
- у каждого параграфа: название + описание 2–3 предложения + норма/практика +
  переход к следующему
- есть «Выводы по главе N» после каждой главы ← **есть в обеих ваших работах**
- нумерация сквозная, без пропусков

**Брак:** параграф без указания источниковой базы; дробление на 6+ параграфов
в главе (мельчит).

✅ **РЕШЕНО (ваш ответ):** стандарт — **3 главы + выводы по каждой**.
Допустимы **2 главы**, если так указано в методичке вуза. Больше, чем
нужно, делать не стоит. Реализовано: `check_plan(required_chapters=...)`
— если методичка задаёт число, оно жёстко проверяется; иначе разрешены
2 или 3, а 4+ идут в брак.

## 3. `introduction` — введение

**Машина:**
- объём **3800–5000 знаков БЕЗ пробелов** ✅ (ваш ответ)
- присутствуют все обязательные элементы: актуальность, цель, задачи,
  объект, предмет, структура ✅ (ваш ответ: обязательны все)
- **гипотеза и её оценка — только для диссертации**; в курсовой гипотеза
  не нужна ✅ (ваш ответ)
- не начинается словом «Введение»
- ≥ 2 ссылки на нормы/источники
- задачи соответствуют главам плана (сверка по числу)

✅ **РЕШЕНО (ваш ответ):** раздел — **5000–6000 знаков БЕЗ пробелов**.
Это снимает противоречие в промпте: старое «7000–10000 без пробелов»
надо заменить на 5000–6000, иначе модель гонится за объёмом и льёт воду.

|---|---|---|---|
| Введение | 3800–5000 | 4336–5705 | 2.4–3.2 |

# Приложение А. Калибровка порогов по вашим текстам

Критерии перенесены в код: `backend/app/modules/ai_engine/acceptance.py`,
тесты — `backend/tests/test_acceptance.py` (32 теста).

## Главный принцип калибровки

**Порог, который бракует ваш собственный текст, — неверный порог.**
Каждый числовой порог прогнан против 30 реальных разделов двух ваших
диссертаций. Где эталон не проходил — двигали порог, а не эталон.

## Что пришлось исправить

Первая версия порогов считалась от **корпуса целиком** и оказалась
непригодной: корпус смешивает разные разделы, поэтому разброс на нём
завышен, а клише — размазаны.

| Порог | Было (по корпусу) | Стало (по разделам) | Почему |
|---|---|---|---|
| Разброс длин предложений | ≥ 12.7 | **≥ 8.7** | у вас есть разделы с 7.5–9.0; порог 12.7 бракует ваш текст |
| Клише на 1000 слов | ≤ 2.0 | **≤ 3.5** (warning с 2.5) | медиана ваших разделов 1.87, p75 = 2.92, max 5.18; порог 2.0 бракует 40% |
| Доля коротких предложений | брак | **предупреждение** | по разделам сильно плавает |

Замеры по 30 разделам:
- разброс длин: медиана **14.7**, p10 **8.7**, min 7.5, max 36.6
- клише/1k: медиана **1.87**, p75 **2.92**, p90 3.75, max 5.18

**Результат:** стилевые пороги проходят **70%** ваших разделов
(было 50%). Оставшиеся 30% — ваши самые «плотные» разделы; они получают
предупреждение, а не брак, и конвейер не останавливают.

Детектор при этом не ослеп: синтетический ровный машинный текст
(40 предложений одинаковой длины) по-прежнему уверенно бракуется —
на это есть отдельный тест `test_machine_flat_text_still_caught`.

## Об объёмах: расхождение, которое нужно знать

Ваши пороги (введение 3800–5000, раздел 5000–6000 знаков б/п) —
**курсовые**. Ваши собственные диссертации вдвое объёмнее:

| | Введение (б/п) | Медиана раздела (б/п) | В диапазон 5000–6000 попало |
|---|---|---|---|
| Дисс. 2026 (право) | 9 468 | 11 468 | 0 из 10 разделов |
| Дисс. 2002 (эконом) | 10 749 | 7 500 | 1 из 20 разделов |
| **Ваш порог** | 3800–5000 | 5000–6000 | — |

Это не противоречие: для курсовой ваши цифры разумны, диссертация —
другой жанр. Но если сервис будет генерировать и диссертации, для них
понадобится отдельный набор объёмов. В коде это уже заложено через
`WorkKind.coursework` / `WorkKind.thesis` — сейчас различаются только
требованием гипотезы, объёмы при необходимости разведём тем же ключом.

## Побочно найден и исправлен баг парсера

Разбор структуры глав дал у диссертации 2026 «главы 53 и 61»: строки
вида «61.11 Закона о банкротстве» и «53.1 Постановления Пленума»
распознавались как номера разделов. Регулярка ограничена
(`^[1-9]\.\d{1,2}`) — юридические ссылки больше не ловятся. Теперь обе
работы разбираются как **ровно 3 главы**, что подтверждает ваше правило.

# Приложение Б. Предварительные настройки работы

Часть ваших ответов звучала «зависит от темы» и «где уместно». Такое
нельзя зашить константой, поэтому появился модуль настроек:
`backend/app/modules/projects/preferences.py`. Он — единственный
источник правды для проверок; пороги больше не дублируются в двух местах.

## Ответы, ставшие кодом

| Ваш ответ | Как реализовано | Поведение по умолчанию |
|---|---|---|
| Клише — «не выше авторского» | `cliche_policy` | `author_level`; жёсткий ноль — опция, не умолчание |
| Тезисы — «зависит от темы» | `theses_per_section` — диапазон | 3–8; сложной теме ставим 6–12 |
| Главы — «2 или 3» | `chapters=None` → разрешены 2 и 3 | 4+ брак; методичка задаёт число жёстко |
| Кейсы — «могут быть, а могут и не быть» | `cases` | `when_relevant` — наличие не требуем |
| Таблицы — «там, где уместна» | `tables`, `charts` | `when_relevant` |
| «Пустые таблицы не нужны» | `forbid_empty_visuals` | таблица с <2 строками данных или с ячейками-заглушками — брак |
| Предложения по закону — «желательны, но обоснованы» | `law_proposals` | для юр. работы: нет предложений — предупреждение; есть, но без обоснования — **брак** |

Ключевая деталь по последнему пункту: проверяется не наличие слова
«предлагается», а связка предложения с проблемой. Формулировка
«Предлагается дополнить ст. 61.10» без объяснения, какой пробел она
закрывает, не проходит — это декларация, а не предложение.

Требование из трёх состояний (`required` / `when_relevant` /
`forbidden`) вместо галочки — потому что «обязательно» и «не нужно» не
покрывают ваш ответ «где уместно». Это третье состояние, а не
компромисс между двумя.

## API для интерфейса

- `GET  /api/v1/projects/preferences/schema` — описание полей и подсказок

- `POST /api/v1/projects/preferences/validate` — проверка + сводка;

Пресеты: `coursework_legal`, `coursework_economics`, `thesis_legal`.

# Приложение В. Настройки до генерации: методичка и пожелания

Реализовано в `backend/app/modules/projects/methodichka.py`.

## Три источника вместо одного

| Источник | Что даёт | Пример |
|---|---|---|
| **Методичка вуза** | жёсткие формальные требования | «работа должна состоять из двух глав» |
| **Пожелания клиента** | свободный текст | «побольше практики, без воды» |
| **Форма** | явный выбор галочками | `chapters = 3` |

Приоритет: `умолчания < пресет < методичка < пожелания < явный выбор`.
Явный выбор побеждает всегда — распознанное из методички не должно
молча переписывать то, что человек указал руками.

## Каждое решение с обоснованием

Парсер текста ошибается, поэтому любое распознанное требование несёт
цитату из методички и уровень уверенности. Пользователь видит, на каком
основании выставлено значение:

```
• chapters = 2
    основание: «Курсовая работа должна состоять из двух глав…»
• cases = required
    основание: «Обязательно использование судебной практики…»
```

Ответ API содержит `needs_confirmation: true`, если что-то распознано, —
интерфейс обязан показать это на подтверждение, а не применять тихо.

## Что распознаётся сейчас

- вид работы (курсовая / ВКР / диссертация);
- предмет (юридический / экономический);
- число глав;
- объём в страницах → пересчёт в знаки без пробелов;
- выводы по главам, обязательность практики, таблиц, предложений
  по законодательству;
- гипотеза в методичке → работа считается квалификационной.

Из пожеланий: «больше практики», «без таблиц», «без воды», «живее»,
«строго научный стиль», «две главы».

Объём в страницах пересчитывается честно: из общего объёма вычитаются
титульник, содержание, список источников и приложения (~20% и 4
страницы), остаток делится на разделы. Промежуточный расчёт
показывается пользователю в `notes`, а не прячется.

## API

```
POST /api/v1/projects/setup
{
```
